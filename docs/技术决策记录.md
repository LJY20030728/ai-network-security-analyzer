# 技术决策记录（ADR）

> **这份文档的用途**：记录每个关键决策的**取舍与代价**，以及**实测数据**。
>
> 华为技术面的特征是"不换题、只往深处追"——面试官会顺着一个技术点连续追问
> 到你答不出来为止。因此本文件刻意按"**能追问三层**"的标准组织：
> 每个决策都写清「备选方案 → 为什么选它 → 代价是什么 → 怎么验证的 → 追下去会撞到什么边界」。
>
> **用法**：面试前通读一遍，重点记「代价」与「边界」两栏 —— 那是最容易被问穿的地方，
> 也是主动说明时最能体现工程素养的地方。

## 决策 1：流式解析而非全量加载

**背景**：需要处理可能超出内存的 PCAP 文件。

| 方案 | 优点 | 缺点 |
|------|------|------|
| A. 全量 `rdpcap` 后分析 | 实现简单，可随机访问 | 内存 ∝ 总包数 |
| **B. `PcapReader` 单遍流式（采用）** | 内存 ∝ 活跃流数 | 实现复杂；不能回头访问历史包 |

**为什么选 B**：内存上界与总包数**解耦**，这是"能处理 GB 级 PCAP"的**唯一**依据。

**实测（`tools/bench_stream.py`，30 万包 / 28.1 MB PCAP）**：
```
全量加载  380.8s  →  1207.7 MB     告警 15
流式解析  325.3s  →    18.6 MB     告警 15     内存降低 65.0 倍，告警完全一致
```

> ⚠️ **耗时数字不可作为结论**：同一份文件在本机不同时间测得 244.0s 与 325.3s
> （相差 33%），绝对耗时受机器负载影响很大。`speedup_x=1.17` **不应被解读为
> "流式更快"** —— 它只是这一次测量。可靠的结论只有两条：
> **内存峰值降低 65 倍** 与 **告警结果一致**。

**代价（面试要主动说）**：
- 流式省的是"原始包对象"，换来的是"流表"。**流表大小 ∝ 活跃五元组数**，
  所以这个 65 倍是**一份具体样本**的结果，不是普适保证。
  四种样本实测压缩比：`largeflow` 0.00 / `normal` 0.15 / `demo_normal` 0.54 /
  `demo_attack` **1.00**（每包一条流时几乎没有压缩）。
- **流表当前无上界、无超时淘汰** → 对五元组基数极高的流量，内存仍会增长。

**追问链准备**：
```
Q: 流式省内存吗？
A: 省，但取决于包/流比。内存上界 ∝ 活跃流数，与总包数解耦。
Q: 省了多少？
A: 30 万包样本上 1207.7 MB → 18.6 MB；但构造样本每包一条流时压缩比是 1.00。
Q: 那流表的边界在哪？    ← 【危险问题】
A: 目前没有边界 —— 这是已知缺陷。正确做法是给流表加 LRU 上界 + 流超时淘汰
   （`flow_timeout` 参数已存在但未用于淘汰）。加上之后才是真正的 O(1)。
```

## 决策 2：三引擎融合（**证据强度已如实标注**）

**背景**：单一判据必然有结构性盲区。

| 引擎 | 判据 | 能回答 | 结构性盲区 |
|------|------|--------|-----------|
| 规则 | 阈值 | 这是**已知**攻击吗 | 变种 / 慢速 / 未知 |
| 时序基线 | 相对自身历史的 z 分数 | 今天**与往常不同**吗 | 首次出现即失效 |
| 孤立森林 | 多维联合稀疏度 | 这组合我**没见过** | 无法给出因果 |

**关键区分**：这不是"三个准确率取平均"，而是**三种认知范式**互补。

**实测（`tools/ablation_engine_subsets.py`，1368 窗，与训练同口径）**：

| 组合 | 维度 | F1 | ±std | 漏报 |
|------|------|-----|------|------|
| 仅规则 | 4 | 0.7121 | 0.147 | 204 |
| 仅时序基线 | 3 | 0.6772 | 0.186 | 210 |
| 仅孤立森林 | 6 | 0.6332 | 0.296 | 165 |
| 规则 + 基线 | 7 | 0.7121 | 0.147 | 204 |
| **规则 + 孤立森林** | 10 | **0.7831** | 0.216 | **44** |
| **三者融合（生产）** | 13 | 0.7425 | 0.270 | 48 |
| *平凡地板：全判攻击* | — | *0.6535* | — | — |

**能说的**：
- 全部组合高于平凡地板 → 特征有真实判别力
- 加入孤立森林后**漏报 204 → 44**（跨全部折一致，是量级差异）
- 2 个特征恒为常数（`baseline_drifted`、`isolation_available`）→ 零贡献

**不能说的（务必主动声明）**：
- ❌ **不能宣称融合最优**：它比"规则+孤立森林"低 0.0406，
  而**组间差异 0.03 < 折间标准差 0.15–0.27** → 不构成显著差异
- ❌ 不能宣称时序基线无用（只能说其增量无法与零区分）
- ❌ 不能据此调生产配置（17 个样本组太少，折间 F1 波动达 [0.32, 0.98]）

**这个"无法判定"的结论本身就是工程素养的体现**：小样本做消融，
最大的风险是把折间噪声读成效应。脚本内置了显著性判定，
差异小于噪声时**直接输出"无法判定"**，而不是硬给一个结论。

## 决策 3：单一分析流水线

**背景**：曾经有三份独立实现（API 同步/异步、UI 流式、历史重生成）。

**问题（真实发生）**：三者在 kwargs、是否流式、**是否跑输出校验**上互不一致，
导致**同一个 `case_id` 可能产出两份正文不同、证据链互相矛盾的报告**。

**决策**：抽出 `src/services/analysis_service.py` 作为唯一实现，UI 层只负责展示与持久化。

**代价**：需要重构；进度反馈要通过回调传递（`_progress` 参数）。

**验证**：`tests/test_analysis_service.py` 断言两条路径都跑校验。

## 决策 4：报告生成硬失败

**背景**：HTML 报告可能因数据缺失或模板异常而失败。

| 方案 | 后果 |
|------|------|
| A. 留空 html_path | 下载按钮会**退化为"取目录里最新报告"** → 用户可能下载到**别人的案件** |
| **B. `raise RuntimeError`（采用）** | 用户看到明确报错，不会拿到错误证据 |

**这是安全产品的正确取舍**：取证工具里"错误但看起来正常的输出"比"明确的失败"危险得多。

## 决策 5：LLM 不参与检测决策

**决策**：LLM 只做语义报告生成与知识问答，**不参与"是否攻击"的判定**。

**理由**：安全领域不可靠的 LLM 不能做判决。检测由本地三引擎 + Stacking 完成。

**如何验证这一点**：`grep` 检测路径即可确认无 LLM 调用；
三条检测路径（规则/基线/孤立森林）全部是确定性算法或离线训练的 sklearn 模型。

**追问准备**：
```
Q: 为什么不用 LLM 直接判断流量是否恶意？
A: 三个原因 —— ① 不可审计（无法解释为何判恶意）；
   ② 不稳定（同样输入不同输出）；③ 可被提示注入（PCAP 里的 payload 是不可信输入）。
Q: 那 LLM 的价值在哪？
A: 把结构化告警翻译成人类可读的研判叙述，以及 RAG 知识问答。这是它的强项。
```

## 决策 6：输出校验 ≠ 事实核查（**已如实标注**）

**原称**"幻觉控制三件套"，但用 6 类对抗样本实测后发现**对编造内容零识别**：

| 用例 | 校验分 | 判定 |
|------|--------|------|
| 良好应答 | 1.000 | ✅ |
| **虚构技术名**（APT41 / T1055 / T1071） | **1.000** | ❌ 未识别 |
| **编造数值**（9999 告警 / 500GB 外泄 / 假 C2） | **1.000** | ❌ 未识别 |
| 与证据矛盾 | 0.867 | ⚠️ 仍算合格 |
| 空应答 | 0.000 | ✅ |

**根因**：技术名提取器对 **MITRE ID** 返回空 → "未知技术"校验永不触发；
编造数值**根本没有检查项**。

**已做的处理**：README 中改名为"三层输出校验"，并加「能力边界」警示块。
**根治方向（未实现）**：evidence grounding —— 要求回答中每个告警类型 / IP / 数值
都必须在 `anomaly_report` 中出现。

**这一段在面试中的价值**：主动说出"我的校验不核事实"比被追问时承认强得多，
而且它展示了你**做过对抗测试**。

## 决策 7：规则模块抽取（双路径统一）

**背景**：`TrafficAnalyzer` 有两条检测路径：

| 路径 | 调用方 | 规则数（v3.4.3 前） |
|------|--------|-------------------|
| `analyze_packets()` → `_detect_anomalies()` | 脚本、CI | **11 条** |
| `analyze_stream()` | **UI 实际运行** | **5 条** |

**真实后果**：UDP/QUIC 攻击在 **UI 运行时完全检测不到**，
而 CI 全绿 —— 因为 golden 样本里根本没有 UDP/QUIC 样本。

**修复**（两步）：
1. 补齐 6 条规则 + 补 3 个 golden 样本 + 加路径一致性测试
2. 抽出 `src/rule_detector.py`，两条路径调用**同一模块**，从结构上消除不一致

**验证**：`test_two_paths_rule_alert_sets_are_identical` 断言两条路径的
告警类型集合完全相同；字段级对照 13 个样本 × 10 字段差异为 **0**。

**这个案例的通用教训**：**代码重复不只是维护问题，是正确性问题** ——
重复的实现会静默发散，而测试若只覆盖其中一条路径就永远发现不了。

## 决策 8：模型溯源与重训（含稳定性验证）

**背景**：模型溯源停在 `git_sha=4bab4c5`（首个提交），
但此后有 14 个提交，其中包含**可能影响特征语义**的改动：
孤立森林特征 3→6 维、规则模块抽取、大流量告警方向修正。

**做法**：重训一次以刷新溯源。

**结果（意外但更有价值）**：

| 项 | 重训前 | 重训后 |
|---|--------|--------|
| 权重 sha256(16) | `80b3f23d48743911` | `80b3f23d48743911` |
| 系数 / 截距 | — | **逐位完全一致** |
| GroupKFold F1 | 0.7424766967302312 | 0.7424766967302312 |
| `git_sha` | `4bab4c5`（过期） | `6aea06f` |

**结论**：那批改动**没有改变特征语义**，模型参数稳定。
本次重训的实际作用是刷新溯源，同时**证明检测行为不受那批改动干扰** ——
这一点此前只能假设，无法断言。

## 决策 9：条件化打包预构建向量库

**背景**：`data/chroma_db`（66 MB 预构建向量库）被 `.gitignore` 忽略，
而 `build_exe.bat` 用 `--add-data` 引用它 → **CI 干净 checkout 下 PyInstaller 直接报错**：

```
ERROR: Unable to find '...\data\chroma_db' when adding binary and data files.
```

**根因**：资源分三类，此前只有两类有处理方式：

| 类别 | 处理 | 例 |
|------|------|-----|
| 小且必需 | 入库 | `data/baselines/default_baseline.json` |
| 大且可下载 | CI curl | `models/bge-small-zh-v1.5` |
| **可运行时重建** | ❌ **无人负责** | `data/chroma_db` |

**决策**：条件化 —— 目录存在则照常打包（本地/正式发布），
不存在则跳过并**打印告警 + 给出补齐命令**（CI）。

**依据**：`RAGEngine._ensure_seeded()` 在集合为空时会从已入库的
`data/knowledge/docs`（1.4 MB）自动播种，所以不是功能必需。

**代价（已写入告警文案与 README）**：缺省时首启动知识量较少
（内置知识源约 63 块 vs 预构建 1687 块）。

**实现注记**：初版用 `if exist (...) else (...)` 块内 `set`，
**实测得到空参数** —— cmd 在解析整个括号块时一次性展开 `%VAR%`。
改用 `goto` 标签结构。

## 决策 10：元测试强制资源入库

**背景**：同一类缺陷反复发作 —— **本地绿、CI 红**：

| 事件 | 机制 |
|------|------|
| 15 个包结构文件从未入库 | `.gitignore` 的 `_*.py` 误匹配所有 `__init__.py` |
| 5 项测试在 CI 必失败 | `.gitignore` 把产品资源当用户数据（`data/baselines`） |
| 整个测试收集阶段中断 | 拆分出的 4 个 UI 模块从未 `git add` |
| **CI 连续 48 次全红** | 上述问题叠加，而徽章仍写 "passed" |

**共同根因**：代码依赖与版本控制之间**没有任何机制保证一致**，全靠人记住。

**决策**：建 `tests/test_required_assets.py` —— 显式**资源登记表** +
逐项断言「存在 / 被 git 跟踪 / 未被实际忽略」。

**实现注记**：忽略判定用 `git check-ignore`（权威），**不自己复刻 ignore 语义** ——
初版用 fnmatch 实现时漏掉了否定规则 `!pattern`，把已正确放行的文件误报为"被忽略"。
**gitignore 语义（顺序 / 否定 / 目录 / `**`）足够复杂，重新实现只会产生假警报。**

**效果**：在 4 个模块未 `git add` 时**确实变红**（4 项 FAILED），
即它对这类缺陷有真实拦截力，不是装饰。

## 已知局限（主动声明清单）

| 局限 | 实测事实 |
|------|----------|
| 输出校验不核事实 | 编造技术名/数值得满分 1.000 |
| 流表无上界 | 只增不淘汰；内存 ∝ 活跃流数 |
| 异步任务表无淘汰 | `TaskQueue._tasks` 只增不减，每任务缓存约 23 KB |
| **三引擎融合无显著优势证据** | 组间差异 0.03 < 折间噪声 0.15–0.27 |
| 基线选择对 ML 引擎无效 | 三组对照 ML 输出**逐字节相同** |
| 解析是性能瓶颈 | 11673 包：解析 ~2100 ms vs 检测 ~500–660 ms |
| 训练样本量小 | 1368 窗 / 17 组，10 组为合成样本；LOO 泛化 F1=0.5646 |
| 检测范围有限 | 仅流量级 11 类，不覆盖应用层/payload |

**面试策略**：这份清单应当**主动**说出，而不是等被问。
主动说明边界展示的是"知道自己系统的可信范围"，这是安全岗位的核心素质。

## 一句话总结（自我介绍时的项目描述）

> 一个 AI 辅助的网络取证分析系统：单遍流式解析 PCAP，用规则 / 时序基线 /
> 孤立森林三个引擎做互补检测，13 维特征经 Stacking 元学习器融合，
> 再由 LLM 生成威胁研判报告，本地 RAG 支持安全知识问答，最终打包为 Windows 桌面应用。
>
> 我在这个项目里花力气最多的不是检测算法，而是**让系统的可信度可验证**：
> 把 CI 从 48 次全红修到全绿、给模型加 sha256 溯源与数据指纹、
> 建元测试防止"本地绿 CI 红"复发，并如实标注了每一个能力边界
> ——包括实测发现"我的输出校验不核事实"。
