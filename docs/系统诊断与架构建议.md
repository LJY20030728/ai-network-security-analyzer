## 1. 第一性原理：这个系统到底是什么

### 1.1 剥掉表象后的本质

用一句话定义：**这是一个把 PCAP 字节流，转化为"可被人类与事后审计所信任的检测结论"的转换器。**

拆到不可再分的因果链：

```
PCAP 字节
   ↓ 解析            ← 输入保真度（有没有丢包、丢流、丢时间）
数据包 / 流
   ↓ 特征提取        ← 语义保真度（特征是否与训练模型同分布）
特征向量
   ↓ 检测            ← 判定质量（recall / precision / 未知攻击覆盖）
告警 + 置信度
   ↓ 融合            ← 冲突裁决（多引擎矛盾时谁说了算）
最终判定
   ↓ 研判 / 报告      ← 可解释性与证据链
人类可读结论
```

**关键洞察：链条强度 = 最弱一环。** 而这个系统的现实是：链条上有 5 处断裂同时存在（见 §3），所以它现在的整体价值不是"平均分"，而是**接近于零**——因为入口直接抛异常，后面 5000 行代码根本没机会执行。

### 1.2 真正的核心资产是什么

对抗性地问：如果把 UI 全删了，这项目还剩什么价值？

| 资产 | 是否可替代 | 真实价值 |
|---|---|---|
| 检测算法（HistGradientBoosting + 76 维 CIC 特征） | 高度可替代（教科书级做法） | 低 |
| **检测链路的工程闭环**（流式解析 → 特征 → 多引擎 → 报告） | 中等 | 中 |
| **评测方法论与可复现证据**（OOT、跨域、双口径 RAG） | **难以替代** | **最高** |
| LLM + RAG 研判层 | 可替代 | 中（但差异化叙事强） |
| UI / 打包 / 安装器 | 高度可替代 | 低 |

**这就是第一个反直觉结论**：这个项目最值钱的不是算法，而是它**试图对自己诚实**的那部分——OOT 时间外推（F1 从 0.9704 掉到 0.8924）、跨域迁移失败（0.1924）、macro recall 只有 0.4683、如实标注两个 RAG 首位瑕疵。

大厂评审最看重的恰恰是这个：**"你敢不敢报告自己失败的地方"**。而现在的重构正在把这份最值钱的资产删掉（14 个评测脚本已从工作区消失，见 §3.2）。

### 1.3 由此推出的设计公理

| 公理 | 推论 |
|---|---|
| **A1. 结论必须可追溯** | 任何判定都要能回指到 `(输入哈希, 代码版本, 模型版本, 配置快照)`，否则结论无证据效力 |
| **A2. 引擎必须可独立评测** | 无法单独测量的引擎 = 无法证明它有用的引擎（现在恰好如此） |
| **A3. 降级必须显式可见** | 静默 fallback 会让用户以为在用 A，实际在用 B（现在至少 4 处静默降级） |
| **A4. 文档即接口契约** | 文档承诺 ≠ 代码行为 = 工程事故（现在 README 大面积失真） |
| **A5. 复杂度必须换取可测性** | 为复杂度付出的每一分，都要能在测试或指标上收回 |

## 2. 对抗性审查的判定基线

我采用的审查原则（也是建议你今后自审时用的）：

1. **文档是嫌疑人**：README 说的每一句话都要在代码里找到证据，找不到就记为"文档失真"。
2. **注释是嫌疑人**：注释说"F1=0.9487"，就去模型文件里读出真实数字比对。
3. **沉默的失败最危险**：`except Exception: logger.warning(...)` 是掩盖 bug 的头号工具（全项目 **27 处** `except → pass`）。
4. **宁可自己跑一遍**：能实测的绝不推断。本次审查全部关键结论均有实测输出（见 §3 证据栏）。
5. **区分"能跑"与"跑了但你没发现它在骗你"**：后者对安全工具是致命的。

### 3.3 🟠 HIGH：评测体系存在数据泄漏与自我循环

实测 `models/multiscale_lgbm.joblib` 的元信息：

```python
feature_dim      = 84
auc              = 1.0            # ← 完美 AUC，几乎必然是问题
cv_auc_mean      = 1.0
cv_auc_std       = 0.0
best_iteration   = 1              # ← 只用了 1 棵树
best_threshold   = ()             # ← 空元组，不是数值！
training_samples = 900
golden_pcaps     = ['normal.pcap','synflood.pcap','portscan.pcap',
                    'dnstunnel.pcap','largeflow.pcap','rststorm.pcap']
variants_per_pcap= 100
note             = "训练数据仅基于6个golden pcap的变体，样本量有限，不代表真实…"
```

四个独立问题叠加：

1. **训练集与评测集同源**：模型训练在 6 个 golden pcap 的变体上，而 `data/samples/golden/` 恰好又是 README 性能压测与阈值调优用的**同一批**样本。**这不是泛化，这是记忆。**
2. **AUC=1.0 / cv_auc_std=0.0**：真实网络流量不可能出现。这是教科书级的泄漏信号（或合成数据可分性过高）。
3. **`best_iteration = 1`**：LightGBM 只建了 1 棵树。模型实质上是**一个决策 stump**，84 维特征几乎没被利用。
4. **`best_threshold` 是空元组而非 float**：看加载代码 `flow_extractor.py:439`
   ```python
   self._lgbm_threshold = data.get('best_threshold', 0.5)
   ```
   由于 key 存在（只是值为 `()`），`data.get()` 返回 `()` 而非默认值 0.5 → `self._lgbm_threshold = ()`。
   随后 `flow_extractor.py:740`：`is_attack = prob >= self._lgbm_threshold`
   在 Python 3 中 `float >= ()` 会抛 `TypeError`，而该 `try/except` 会捕获并降级为 `{"available": False, "error": ...}`。
   **反直觉结论：这个"阈值 bug"恰好救了你**——它让 L2 引擎整体失效，从而把那个数据泄漏模型挡在了结论之外。但这是**意外**，不是设计。

### 3.5 🔴 CRITICAL：DNS 应答包会让整文件解析崩溃（已验证）

`src/capture/packet_parser.py:97`：

```python
if packet[DNS].qr == 1 and packet[DNS].ancount > 0 and packet[DNS].an:
```

在 scapy 2.7.0（实测版本）下，DNS 应答包的 `ancount` 可能是 `None`（scapy 现已将 `qd/an/ns/ar` 改为 `PacketListField`，实测运行时有 610 条相关 `DeprecationWarning`）。`None > 0` 抛：

```

```

而包裹 `try/except` 的只有 `.rdata` 那两行（`:98-103`），**这个比较不在保护范围内** → 整个 `PacketParser.parse` 中断 → `parse_file` / `iter_packets` 全文件分析失败。

**后果：任何含 DNS 应答的真实 PCAP（几乎等于所有真实 PCAP）都会触发。** 修复一行：`(packet[DNS].ancount or 0) > 0`，或干脆去掉计数判断、只依赖 `.an`。

## 5. 目标架构建议（按第一性原理重新设计）

### 5.1 核心设计主张

**主张一：把"结论"升级为"可复现的证据包"。**

这是整份建议的灵魂。当前系统输出的是"攻击/正常 + 置信度"，无法自证。目标形态：

```
每一次分析产出不可变的 Evidence Bundle（证据包）
├── input_hash       : PCAP 的 SHA-256
├── code_version     : git commit
├── model_versions   : {supervised: sha256, lgbm: sha256, meta: sha256}
├── config_snapshot  : 生效的阈值全集（含默认值来源）
├── engine_verdicts  : 每个引擎的独立判定 + 各自版本
├── fusion_verdict   : 融合结果 + 用了哪个融合器 + 是否降级
├── degradations     : 显式列出本次所有降级事件（A3 公理）
└── report_hash      : 最终报告的哈希
```

**收益**：任何结论都能被第三方复核；同一 PCAP 在两周后重跑，差异必然可归因（代码？模型？配置？）。这一个改动，就能让你的项目从"会写算法"升级为"有工程判断力"——这是大厂面试最想看到的分水岭。

**主张二：单引擎 → 统一注册表 + 可选编排。**

反对现在的"双管线并存"。目标：

```
每个检测引擎实现同一协议：
    name / version / fingerprint(模型hash) / health() / detect(x) -> Verdict
Verdict = {engine, is_attack, confidence, evidence[], degradations[]}

编排器（唯一入口）：
    Pipeline = [Stage(engine, mode=cascade|parallel, threshold)]
    → 声明式配置决定谁先跑、谁短路、谁融合
```

**收益**：新增引擎只写一个类（README 里承诺的"策略模式"才真正成立）；每个引擎可**单独**跑评测（公理 A2）；架构图与代码结构一一对应。

**主张三：评测与运行时解耦，但同源。**

评测脚本必须回归仓库，并做到：
- 统一入口 `pytest tools/eval/ -k <name>` 或 `python -m eval <name>`
- **训练/评测数据严格分离**：golden 样本只允许出现在评测集，绝不能进训练集
- 每个指标必须能**一键重算**并输出到 `data/eval_perf/`，README 的表格由脚本生成而非手写

**主张四：分层收敛为 4 层，拒绝装饰性分层。**

```
┌────────────────────────────────────────────┐
│ 入口层  desktop_app.py / __main__.py        │  ← 唯一入口，支持 python -m app
│         （pywebview + uvicorn 生命周期）      │
├────────────────────────────────────────────┤
│ 接口层  api/  (FastAPI 路由 + Pydantic)      │  ← 只做校验/序列化，不含业务
│         ui/   (Gradio)                      │  ← 只做展示，不做检测逻辑
├────────────────────────────────────────────┤
│ 领域层  detection/  (引擎 + 编排 + 融合)      │  ← 纯函数、可单测、无框架依赖
│         analysis/   (流/特征/基线)            │
│         knowledge/  (RAG + LLM 研判)         │
├────────────────────────────────────────────┤
│ 基础层  core/     (配置/错误/日志/证据包)      │  ← 被依赖，不反向依赖
│         storage/  (SQLite/向量库)            │
└────────────────────────────────────────────┘
```

关键约束（用 CI 强制，而非靠自觉）：
- **领域层禁止 import fastapi / gradio**（`import-linter` 或自定义 lint 一条规则即可）
- **UI 层禁止包含检测算法**（`gradio_app.py` 不得再出现模型推理）
- 配置**只允许一份**：要么分组类生效，要么平铺生效，不能两套并存
